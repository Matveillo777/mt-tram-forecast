# Производительность

## Итог

Один экземпляр backend на **2 vCPU** держит **2000 запросов в секунду при загрузке процессора 49%** и **3000 запросов в секунду при 85%**, без ошибок, с задержкой p95 1.6 и 11.8 мс соответственно. Память процесса стабильна: 417-445 МБ при лимите кучи 1 ГБ, свопа нет. Предел двух ядер около 3300 запросов в секунду.

## Как мерили

- **Нагрузка:** k6, сценарий [loadtest/k6.js](../loadtest/k6.js), постоянный темп запросов (constant-arrival-rate) 60 секунд на каждую ступень.
- **Смесь запросов:**

  | Доля | Запрос |
  |---|---|
  | 35% | прогноз на день по маршруту |
  | 20% | прогноз на месяц по дням |
  | 10% | прогноз на год по месяцам по всей сети |
  | 10% | карта на дату и час (все маршруты и остановки) |
  | 10% | прогноз по остановке с поправками на погоду |
  | 5% | выгрузка CSV |
  | 10% | приём пачки из 100 валидаций (`POST /api/v1/ingest/validations`) |

  То есть на 3000 запросов в секунду сервис одновременно принимает около 30 000 валидаций в секунду.
- **Стенд:** AMD Ryzen 9 7900X, Windows 11, Java 21 (Temurin), `-Xmx1g -XX:ActiveProcessorCount=2`. Процесс backend привязан к двум логическим процессорам (это два потока одного ядра, как vCPU в облаке), генератор нагрузки k6 работает на других ядрах и не отнимает процессор у сервиса.
- **Процессор и память процесса** снимались каждые 2 секунды. Загрузка указана в процентах от двух выделенных vCPU.

## Результаты

| Темп, запросов/с | Получено, запросов/с | p50, мс | p95, мс | p99, мс | Ошибки | CPU (из 2 vCPU) | Память, МБ |
|---|---|---|---|---|---|---|---|
| 1500 | 1499 | 0.5 | 1.7 | 12.1 | 0% | 39% | 417-440 |
| 2000 | 1999 | 0.5 | 1.6 | 7.9 | 0% | 49% | 429-441 |
| 3000 | 2996 | 1.0 | 11.8 | 62.6 | 0% | 85% | 422-445 |
| 4000 | 3273 | 289 | 469 | 596 | 1.7% | 91% | 432-439 |

Перед замером сервис прогревался 20 секунд на 400 запросах в секунду. При 4000 запросов в секунду два ядра насыщены: сервис успевает около 3300 в секунду, остальное копится в очереди. Рабочая точка с запасом из ТЗ (загрузка процессора 60-80%) - около 2500 запросов в секунду на экземпляр.

Запросы без поправок идут по быстрому пути: множители дней не считаются. Запросы с поправками (10% смеси) считают множитель для каждого дня выборки и вклад каждого фактора.

## Почему так быстро

- Прогноз посчитан заранее. Backend при старте читает артефакты (около 0.4 секунды, запуск целиком около 4 секунд) в массивы примитивов по маршруту, дню и часу, а запрос только складывает нужный срез.
- Всё на неблокирующем стеке Spring WebFlux и Netty, в обработке запросов нет обращений к диску и базе.
- Счётчики онлайн-потока без блокировок (`AtomicLongArray` на маршрут x час).

## Масштабирование

Экземпляры backend не хранят состояния (кроме счётчиков онлайн-потока), поэтому масштабируются горизонтально: несколько контейнеров с одними и теми же артефактами за балансировщиком. Для онлайн-потока при нескольких экземплярах счётчики нужно вынести в общее хранилище (см. [план развития](limitations-roadmap.md)).

## Проверка в CI

Тот же сценарий запускается в GitHub Actions ([.github/workflows/ci.yml](../.github/workflows/ci.yml)) после сборки образов и проверки всех точек API: backend работает в контейнере с ограничением `cpus: 2`, `memory: 2g` из `docker-compose.yml`, результат пишется в сводку прогона и в артефакт `loadtest`. На раннере GitHub генератор нагрузки делит процессор с сервисом, поэтому задержки там выше, чем на стенде с выделенными ядрами.

Прогоны 26.09.2026 на 400 запросов в секунду в контейнере 2 vCPU / 2 ГБ, ошибок 0% в обоих:

| Прогон | Запросов | p50, мс | p95, мс | p99, мс | CPU контейнера (из 2 vCPU) | Память, МБ |
|---|---|---|---|---|---|---|
| первая версия сервиса | 24 002 | 0.75 | 10.5 | 141 | 31% | 280-316 |
| с поправками сценариев по дням | 23 903 | 1.37 | 167 | 530 | 43% | 272-315 |

Разброс задержек между прогонами большой: раннер GitHub общий, и k6 на нём делит два ядра с сервисом. Поэтому основные цифры выше сняты на стенде с выделенными ядрами, а прогон в CI подтверждает, что образы собираются, сервис держит нагрузку без ошибок и укладывается в память контейнера.

Повторить у себя:

```bash
docker compose up -d
docker run --rm --network host -v "$PWD/loadtest:/lt" grafana/k6 run -e BASE=http://localhost:8081 -e RATE=2000 /lt/k6.js
```
